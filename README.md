# 万界 Wanjie · AI 文字冒险

**你设定世界，扮演主角，决定下一步。AI 担任主持人，接着讲你的故事。**

[简体中文](README.md) · [English](README_EN.md)

万界是一款由 **DeepSeek** 驱动的文字冒险游戏，在本地浏览器中游玩。你可以自建世界、结识角色、探索与战斗，也可以安排一段时间修炼或生活。世界状态、人物往事与约定会随存档保存，供后续剧情使用。

*A DeepSeek-powered text adventure with custom worlds, persistent character profiles, and code-resolved combat. Currently designed for Chinese-language play.*

## 可以怎么玩？

- **从自己的设定开局**：让 AI 生成世界，上传 JSON / TXT / Markdown 设定，或手动填写；再挑选主角的天赋、体质与特殊能力。
- **用文字决定行动**：自由输入，也可以点击当前情境下的行动选项。探索、交谈、说服、战斗都能推动故事。
- **让重要人物留下档案**：记录性格、说话方式、目标、情绪，以及与你共同经历的事；约定可以被兑现，也可以被打破。
- **选择喜欢的表达**：朴素、标准、文学三档，默认朴素；人物说话时会参考自己的档案。
- **让时间往前走**：通过「岁月模式」安排修炼或生活，由程序推进时间、处理插曲与打断。
- **保存不同的人生**：网页版支持多个存档，以及 JSON 存档导入、导出。

**AI 负责讲述，程序负责掷骰和结算。** 战斗胜负、行动判定、伤害和生死由代码处理，模型根据结果继续叙事。结构化状态与摘要帮助故事衔接；可选的 SQLite 记忆层还能检索历史往事。

## 快速开始

需要 **Python 3.10+**、网络连接和你自己的 **DeepSeek API Key**。模型调用由 DeepSeek 计费；游戏界面和主要提示词目前为中文。推荐使用功能最完整的 **网页版**。

### 1. 下载项目

在 GitHub 点击 **Code → Download ZIP** 并解压，或使用 Git：

```bash
git clone https://github.com/yiboyang57-commits/ai-dialogue-game.git
cd ai-dialogue-game
```

### 2. 启动游戏

安装 Python 后，可以双击项目中的启动器：

- **macOS**：`启动游戏.command`
- **Windows**：`启动游戏.bat`

启动器会在首次运行时创建环境、安装依赖并打开浏览器。也可以手动启动：

**macOS / Linux**

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m streamlit run app.py
```

**Windows（PowerShell）**

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m streamlit run app.py
```

### 3. 填入 Key，开始新游戏

首次打开后按提示输入 DeepSeek API Key，再选择世界观、创建主角。Key 保存在本地 `config.json`；也支持环境变量 `DEEPSEEK_API_KEY`。存档保存在本地 `save/` 中；游玩时会把剧情所需的上下文发送给 DeepSeek。

`config.json` 和 `save/` 已被 Git 忽略，分享项目或反馈问题时不要附上自己的 Key。

## 架构设计

### 1. 结构化状态管理 —— `world_state.py`
世界状态保存在 `save/state.json`，包含：世界背景、玩家（属性/状态效果）、当前地点、
时间、已知角色、背包、剧情标记（`plot_flags`）、当前目标、故事摘要、事件日志。
一致性靠这份 JSON，而不是完整对话历史。

### 2. 每轮流程 —— `game.py` + `tools.py`
每轮只发送：**当前状态摘要（由 JSON 实时生成）+ 最近几轮对话 + 玩家最新输入**。

模型输出两部分：
1. 给玩家看的叙事文本；
2. 通过 **function calling** 显式调用 `update_world_state(...)` 工具，返回结构化状态增量。

`apply_update` 用「增量合并」策略把增量写回 JSON（只改模型明确给出的字段，其余保留）。
如果模型偶尔忘记调用工具，会自动重试一次；仍失败则报错并回滚本轮，可重新尝试。

### 3. 历史压缩 —— `memory.py` + `game.compress()`
- `recent` 只保留最近 3 轮完整对话（`KEEP_RECENT_ENTRIES = 6` 条）。
- 每累计 `COMPRESS_EVERY_TURNS = 20` 轮，把这段时间的对话交给模型压缩，同时产出
  「本章摘要」（滚动保留最近 `MAX_CHAPTER_SUMMARIES` 段）与「全局摘要」（`narrative_summary`）。
- 上下文因此被约束为：状态摘要 + 章节摘要 + 全局摘要 + 最近几轮；角色/背包/标记在摘要中截断，
  即使长局也不会无限增长。

### 4. 战斗判定 —— `combat.py`（隐藏计算，不显性展示）
- 战力体系在世界生成时锚定（`combat`：量纲 `field`、主角战力 `player_power`、段位差 `realm_gap`、曲线 `curve`）。
- 战斗/逃跑由**代码掷骰**判定（sigmoid 曲线：段位越高，跨段位翻盘概率越低），
  模型只负责叙述与记录，**不得自行决定结局**；概率数值与公式不发给玩家、也不发给模型。
- 战斗回合为「两次调用」：第一次声明敌人，系统判定后第二次叙述结果并记录战后状态。

### 5. 持久化 —— `save/` 目录
- `save/state.json`：世界状态（含战力锚定、章节/全局摘要、事件日志、最近战斗）。
- `save/history.json`：近期对话窗口 + 待压缩缓冲。
- 下次运行检测到存档会询问是否继续（读档恢复）。

### 6. 多存档隔离 + 网页版导入导出 —— `save_bundle.py`

- **多存档隔离**：`WorldState` / `Memory` 支持 `save_key`（存档名）。填了存档名后，
  状态/记忆会写到 `save/state_<存档名>.json`、`save/history_<存档名>.json`，不同玩家互不覆盖；
  留空则沿用原来的默认槽 `state.json` / `history.json`（CLI、GUI 不受影响）。
- **网页版导出/导入**：Streamlit 云端磁盘是临时的，因此网页版在侧边栏提供
  「导出存档」（把世界状态 + 对话历史打成 JSON 下载到自己设备）与「导入存档」（读回恢复进度），
  由 `save_bundle.dump_bundle / load_bundle` 实现，跨设备/跨重启也能继续玩。
- 网页版玩法：每人先在侧边栏填一个**不同的存档名**（如 `alice` / `bob`），再开始游戏；
  「继续存档」只读自己那个存档名下的档。

## 世界观模板（上传 / 生成统一格式）

三种来源（AI 生成、文件上传、手动输入）最终都归一化为同一份「世界观模板」，
字段与状态结构一一对应。上传 JSON 可参考 [`world.example.json`](world.example.json)：

```jsonc
{
  "world":  {"name": "...", "background": "...", "rules": "...", "style": "..."},
  "player": {"name": "...", "role_description": "...", "attributes": {"hp": 100}},
  "initial_situation": "...",
  "location": {"name": "...", "description": "..."},
  "time": "...",
  "characters": {"角色名": {"description": "...", "attitude_toward_player": "...", "location": "...", "status": "..."}},
  "inventory": [{"name": "...", "quantity": 1, "description": "..."}],
  "plot_flags": {"标记": true},
  "current_goal": "...",
  "combat": {"field": "修仙境界", "player_power": 10, "realm_gap": 5, "curve": "realm_gap"}
}
```

只有 `world.background` 或 `initial_situation` 两者至少其一为必填，其余可省略。

`world.style` 是**主持风格**（语气/文风/节奏），与世界观绑定：AI 生成时一并产出匹配的文风；
上传 JSON 可自带；留空则由主持人根据背景自动匹配。系统提示不再强制固定篇幅/句式。

`combat` 锚定战力体系（可省略则用默认值）；货币与道具一样放在 `inventory`，
用 `quantity` 表示数量，例如 `{"name": "金币", "quantity": 50}`。

## 主角构建 —— `character_builder.py`

选定世界观后、正式开局前，会让玩家构建主角基本信息，三类选项都定义在 `character_builder.py`：

| 类别 | 选择方式 | 效果 |
|------|---------|------|
| **天赋** | 多选 0~3 个（如「天命之子」「神机妙算」「炼器天才」…） | 名称对应 `judgment.TALENT_MODIFIERS` 的系数，影响各类判定成功率 |
| **体质** | 单选（如「均衡之躯」「先天道体」「纯阳之体」「霸绝武体」…） | 可带来属性（如生命上限）、初始战力或判定加成，写入 `player.physique` |
| **金手指** | 单选（「无」/「随身系统」/「天机推演」/「存档读档」/「天命气运」/「点石成金」） | 主角独有的外挂/优势，写入 `player.golden_finger`，带来全局或分类型判定加成 |

- **随机 roll**：`roll_talents() / roll_physique() / roll_golden_finger() / roll_build()` 可一键随机生成整套构建，
  三个界面（网页 / GUI / CLI）都提供「随机」入口，避免每次都只能从固定列表里挑。
- **自定义**：天赋 / 体质 / 金手指都支持直接输入自定义名称（网页与 GUI 有输入框，CLI 直接打字）。
  自定义项没有预置数值加成，但会写进状态并注入系统提示，由主持人按名字自由发挥。

构建结果通过 `build_player()` 合并进世界观模板（覆盖模板自带的天赋），最终落到状态里的
`player.talents` / `player.physique` / `player.golden_finger`；体质与金手指同样参与判定（`game._talent_names`
会把三者一起交给判定引擎），并注入系统提示让主持人合理体现，但**不会写出数值**。
可选项、系数都集中在一处，想增删改只需编辑 `character_builder.py` 与 `judgment.py` 的 `TALENT_MODIFIERS`。

开局等待文案也会按世界观题材自动变化（`world_gen.world_loading_phrase`）：
修仙→「天道演变中…」、古风王朝→「王朝更迭中…」、赛博朋克/科幻→「星轨校准中…」、
蒸汽机械→「齿轮转动中…」、悬疑→「迷雾渐浓中…」、都市→「霓虹渐起中…」等。

## 背包按数量增减（货币友好）

`update_world_state` 的 `inventory_add` 累加数量、`inventory_remove` 按 `quantity` 扣减，
**不再整类删除**（仅显式 `remove_all: true` 才会彻底丢弃某物，货币不要用它）。
因此货币（金币/灵石/元宝…）就是普通的数量型道具。

## 主持人限制条件 —— `gm_rules.json`

主持人必须遵守的限制独立于世界观，放在可编辑的 `gm_rules.json`（首次运行自动生成默认值）。
例如：不替玩家做决定、不机械降神、不无端跳时间、失败/死亡要公平等。
直接编辑该文件的 `rules` 数组即可增删；游戏内用 `/rules` 查看当前生效的规则。

> **内容定位：本作面向成年玩家，不设内容分级 / 尺度限制。**
> 主持人的叙事尺度由世界观、玩家引导与你自己写的规则决定。
> 如需重新引入约束，在 `gm_rules.json` 的 `rules`（以及 `gm_rules.py` 的 `DEFAULT_RULES`）里添加即可。

## 概率判定引擎 —— `judgment.py`（拟合因素 + 天赋/道具系数 + 大保底）

亲密关系、寻宝、说服、潜行、洞察、炼制、危险尝试等**成败不由主持人随意决定**，而是由代码把
「影响因素」拟合成概率、掷骰判定（对玩家隐藏）。判定**不写死**：所有权重/系数都在 `judgment.py` 的表中，可增删。

- 概率模型：`logit = base + Σ(因素权重 × 因素值) + 天赋系数 + 道具系数`，`p = sigmoid(logit)`。
  因素值由主持人声明为 `-3~+3` 整数（很不利 ~ 很有利）。
- 亲密关系默认 `base` 极低（刚见面建立亲密关系几乎不可能），并结合性格/场景/家庭背景/身份/好感度等因素。
- **天赋**（如「天命之子」）作为全局或分类型 logit 系数叠加，大幅提升成功率；开局天赋在 `player.talents` 锚定。
- **体质 / 金手指**（主角构建自选）同样以名字挂进 `TALENT_MODIFIERS` 参与判定，与天赋一起由 `game._talent_names` 收集。
- **一次性法宝/特殊道具**（如「护身符」「爆元丹」）在战斗/判定时按名查找系数，使用后消耗；常驻道具（如「寻宝罗盘」）被动加成。
- **渐进保底**：同一类判定连续失败会逐步提高成功率（每类按阈值均分、上限 +3 logit），不再达到阈值就必成；保底计数持久化在 `state.pity`，读档继续累计。

战斗判定（`combat.py`）同样接入天赋与一次性法宝系数。

## v2.25 · 朴素文风与角色档案

- 网页手动建世界和 AI 生成世界都能选 **朴素 / 标准 / 文学**，默认朴素；旧存档也默认朴素。旁白直接说事，人物的说话方式由自己的档案约束。
- 普通角色出场三次、发生关系事件、积累两条往事或达成约定后，可升格为有档案的角色；模板人物在首次叙事出场时升格。最多 20 个完整档案，每回合最多补全一个，需要额外一次模型调用。
- 性格、说话方式、在意的事和底线生成后冻结；目标、情绪可以变化。正式人物转变需要已有剧情理由和 30 回合间隔，并留下修订记录。生成失败不回滚剧情，最多重试三次。
- 模型每轮最多看到四张相关人物卡，每张不超过 180 字；其余角色简列。角色档案不直接展示给玩家。
- 约定记录双方、内容与期限，支持兑现、失约及逾期提醒。逾期不自动判失约；玩家守约 +8、失约 −12，与其他关系事件共同受单轮 ±30 限制，界面仍只显示定性信息。
- 人物未经证实的自述标为「他的说法（未证实）」，保留与事件事实的区别。
- 所有功能首先写入 JSON，关闭 SQLite 也可使用；开启时同步档案和约定事实，保持精确回放。

自动测试 **178 项通过**。真实文风改善和人物区分度尚待作者手动付费评测；固定剧本、运行命令及指标状态见 [文风评估](docs/style_eval.md) 与 [人物盲测](docs/voice_eval.md)。

## v2.23 · 存储阶段 1 第一步：SQLite 事件层

> 实现说明与实测数据：见 [`存储与记忆_阶段进展.md`](存储与记忆_阶段进展.md)。

对应路线图阶段 1 的第一步，**不改变任何游戏行为**：JSON 仍是唯一主存储，
SQLite 作为可选的「历史 / 审计 / 恢复」层。

- 开启方式：`WANJIE_STORAGE=sqlite .venv/bin/python -m streamlit run app.py`
  （默认关闭；v2.24 起失败记录日志并提示，不影响游戏）。
- 一个存档 = 一个 `save/game_<槽>.db`：每回合记叙事、玩家输入、状态增量；
  战斗/判定的掷骰概率与结果也入库，方便复盘；每 10 回合写完整快照。
- 迁移旧存档：`.venv/bin/python scripts/migrate_json_to_sqlite.py --all`
- **实体 / 事实 / 检索**：每回合从状态差异生成「谁在哪里、态度如何、持有什么」的事实时间线
  （`entity_profile(name)`），并支持全文检索往事（`recall(query)`，FTS5 trigram，1~2 字回退 LIKE）。
- **每轮自动召回**：开启 SQLite 后，每轮会按「相关度 + 重要度 + 时间衰减」从历史里
  取 ≤5 条相关往事（人物事实变化、最近提及原文、全文命中），插在状态摘要与最近 3 轮之间，
  预算约 1500 token；关闭存储时行为与旧版一致。
- **每轮剧情概括**：模型每轮额外返回一两句话的 `turn_summary`，入库并参与全文检索；
  检索时优先用概括作为片段（短、含关键词），正文原文仍完整保存可查。
- 尚未替换 JSON 主存储；分层摘要与语义检索留到下一步。

## v2.22 · 逻辑加固（把裁决权收回代码）

按 `archive/逻辑审查_任务书.md` 修复 P0×4 + P1×8，测试从 57 例增加到 91 例。要点：

- **系统独占字段收紧**：`characters.affinity / met_turn`、`player_power`、`max_hp` 模型写不进来（或只允许小幅变化）；
  好感只能通过 `relationship_events` 由代码换算。
- **战斗**：胜利伤害随优势衰减（碾压无伤），**胜利永不致死**；伤害按生命上限的百分比结算。
- **受伤判定改档位制**：`failure_severity = light/medium/heavy` → 生命上限的 10%/25%/45%，模型不再填具体伤害数值。
- **判定更抗刷**：未知因素 / 全部因素的贡献都有上限；保底从「必成」改成渐进加成；
  关系事件同一人单轮只结算最强一条（好感单轮变化 ±30）。
- **更少丢信息**：状态摘要保留最近的剧情标记与物品；场景模式里经过的整天（`days_passed`）计入日历与年龄；
  网页刷新后按地址栏 `?slot=` 自动读回上一局，对话区会接上最近几轮原文。
- **属性参与判定**：福缘、魅力不再只是给模型看的摆设——寻宝/说服判定会按属性数值换算成
  判定因素（每 10 点 ≈ ±1，缺失按普通人水准算），并由代码覆盖模型填写。
- **更稳的后台**：压缩连续失败会退避、缓冲有上限；网页启动时自动清理 7 天前的临时存档；
  背包扣减不会出现负数量（钱不够会记一条「不足」事件给模型看）；敌方战力与伤病档位都有合法性检查。

详见 [`更新记录.md`](更新记录.md) 的 v2.22 一节。

## 去数据化（角色不显性展示数值）

内部数值（hp/战力/好感度/概率/伤害等）只存在 `save/state.json` 供系统与模型使用，
玩家可见的叙事与 `/state` 均用**定性语言**（如「受伤」「好感=高」「气色尚可」），不暴露具体数字。

## 世界观模板柔性化（不写死排版格式）

上传的 JSON 不强套固定模板：已知字段（world/player/combat/talents/…）会被识别并使用，
**未知字段原样保留进 `custom`**，并注入系统提示让主持人遵循；只有玩家未自定义时，系统才按 AI 生成的结构自由决定。

## 动态系数 —— `dynamics.py`（好感度等随事件/时间增减）

- 好感度 = 基础值 + 相识时长加成（每 5 回合 +1、封顶 +15）+ 关系事件增减。
- 关系事件：`RELATION_EVENTS` 表（救命之恩/并肩作战/赠礼/冒犯/背弃…），模型在
  `relationship_events` 写 `{subject, event}`，系统自动换算并钳制 0~100。
- 其它系数：`attribute_events`（声望/魅力/福缘/体力/修为…）按事件或显式 delta 增减。

## 每轮可选行动（帮助游玩）

模型每轮在 `options` 给出 2~4 个**显而易见**的下一步行动，CLI 用 `1) 2) 3)` 展示，
玩家输入数字即可选择，也可输入自定义行动；选项不含隐藏线索/隐藏剧情触发。

## 打包为可执行文件（PyInstaller）

> ⚠️ 平台限制：PyInstaller 只能**在目标系统上**打包 —— Windows 上才能打出 `.exe`，macOS 上打出 `.app`。
> 当前仓库在 macOS 上，故不能直接产出 Windows `.exe`；请在 Windows 机器上执行下面命令。

```bash
pip install pyinstaller

# macOS → 一键打包 dist/AI对话模拟器.app（单文件自包含、双击即用）
python3 make_icon.py     # 可选：生成自定义图标 icon.icns
./build_macos.sh

# Windows → dist/AI对话模拟器.exe（无控制台；需在 Windows 机器上执行）
pyinstaller game.spec
```

> macOS 采用**单文件自包含**打包（`.app` 内部无软链），可避免桌面 iCloud 同步把 bundle 内
> 软链（如 `base_library.zip`）破坏导致运行时报错。CA 证书已随程序内置（`cacert.pem`），
> 不依赖系统 / anaconda 的证书路径。

打包后：`config.json`（API Key）与 `save/`（存档）会生成在**可执行文件同级目录**（代码已处理 PyInstaller 的路径差异）。
首次运行仍会在图形界面里弹窗让你输入 API Key。

## 可调参数（`config.py`）

- `KEEP_RECENT_ENTRIES`：保留的最近对话条数（默认 6，即 3 轮）。
- `COMPRESS_EVERY_TURNS`：多少轮压缩一次（默认 20）。
- `MAX_EVENT_LOG`：事件日志条数上限（默认 15）。
- `MAX_CHAPTER_SUMMARIES`：章节摘要保留条数（默认 6）。
- `DEFAULT_MODEL`：模型名（默认 `deepseek-chat`）。

- 战斗曲线拟合参数在 `combat.py` 的 `CURVES` 中，可自行调；判定过程对玩家隐藏。
- 非流式输出：每轮会短暂显示「主持人思考中…」后一次性输出（战斗回合会多一次判定+叙述，稍慢）。

## 行动节奏与死亡结局（v2.15）

每轮只处理玩家本次输入的行动和直接后果，完成后等待下一次输入。
例如“打一只小怪”不会授权自动拾取、赶路、接任务或跳到几天后；明确的等待、旅行、睡眠、闭关仍会推进该行动所需的时间。

判定回合的第一次回复作为内部草稿，系统结算后再输出一个完整结果。最终续写会收到原行动、判定对象、近期对话与当前状态，选项也以结算之后的场景为准。

玩家没有主角保护：致命战斗耗尽生命，或危险行动失败且后果为死亡时，会记录 `player.life_status = "dead"` 和死因，清空行动选项，并结束这段人生。
明确的非致命训练/切磋可通过 `combat.lethal = false` 结算昏迷；这不能用于回避真实的致命危险。
普通非战斗失败仍可累计保底，但受伤或死亡风险、确定无法完成的行为不享受强制成功。

已有“古玉护佑”天赋可抵挡一次致命战斗伤害，留下重伤；次数记录在 `player.death_protections_used`，之后不会靠模糊的冷却描述反复触发，也不能抵消无保护的千丈坠崖等环境死亡。
已实现能力的默认次数表在 `judgment.DEATH_PROTECTIONS`；状态中的能力条目可显式设置 `death_protection_uses`（1~3次）。未实现的复活类能力不会由主持人临时发挥成无限免死。

`judgment` 支持 `failure_consequence`（`setback` / `injury` / `death`）、`failure_severity`（`light` / `medium` / `heavy`，实际伤害由代码按生命上限比例结算）、`certain_failure` 和 `reason`。
致命危险的识别仍由主持模型依据已有环境与能力声明，系统负责执行结算和死亡状态。
第二阶段 API 失败会撤销该回合未完成的扣血、道具消耗与保底变化，可以重试；历史压缩失败则保留缓冲，下一轮继续尝试。

本次生命结束后仍可保存/导出记录、读取另一份存档或开始新游戏。旧存档可继续加载；现有生命值为零的记录会被视为已结束。

## 网页版候选随机（v2.16）

天赋、体质、金手指分三次独立请求同时生成，目标分别为24、18、18项，避免一次生成整池导致回复被截断。
候选按名字去重，每类至少补足18项；某类生成失败时只补充该类的备用候选，并在页面说明。

“重新随机”在当前池中换一组9张卡片，优先换入至少3个上一组没有的候选；锁定的卡片保留。
已选项不会被换组覆盖，可以通过“移除”按钮取消，即使它已不在当前9张卡片中。
本地换组不调用API。“重新生成候选池”才会再次生成三类候选，并提示模型避开上一批名字，同时清空选择与锁定。
旧会话里的小池或重复卡片会在打开构建页时自动修复。

- **生命值只由系统结算**：普通回合（没有战斗/判定）主持人不能扣血或让主角死亡，只能回血，且不超过原有上限；受伤和死亡必须经过战斗或危险判定掷骰。

## 岁月模式（v2.20）

时间推进分两种：**场景模式**仍是原来的一行动一回合、时间按片刻走；
**岁月模式**用来安排一段较长的时间（一旬 / 一月 / 一季 / 半年 / 一年，或自己填任意天数）。

在输入框下方展开「安排一段时间」，填上「做什么」、选时长、可选「闭关」，点开始即可。
之后由**代码**按旬（10 天）逐段掷随机事件：

- **小插曲**（听到传闻、小有感悟、灵气异动……）不打断，由主持人一笔带过；
- **打断事件**（来访、求助、寻衅、机缘、变故、修行异状……）会把时间停在那一旬，
  输入框下方出现「继续：{计划}（还剩{时长}）」，处理完当前场面后可以接着把剩余时间过完；
- 经过多少天、年龄增不增、休养回多少血，全部由系统结算，主持人只负责把这段日子写出来。

危险不会被跳过：岁月结算本身不会致死，但被打断后的场面照常走战斗 / 判定结算。
主持人还会在 `offscreen` 里记录玩家不知道的幕后进展（谁在打探、哪个势力动了手），
这些内容只用于让它后续合理地透露，不会直接显示给玩家。

概率与事件表都在 [`seasons.py`](seasons.py) 里，可直接增删调整。
每次改动的原因与位置详见 [`更新记录.md`](更新记录.md)。
