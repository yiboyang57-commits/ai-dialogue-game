## C1 朴素文风

### 现象

模型习惯把普通交流写成这样：

> 她眸光微动，似有千言万语，终是化作一声轻叹：「你来迟了。」

作者想要的是：

> 「你怎么才来？」

一部分原因在提示词本身：`prompts.SYSTEM_PROMPT` 的【叙事质量】要求「写具体的动作、声音、气味、触感与画面」，【内容尺度】里有「保持文学性」，世界观模板的 `style` 还常带「古典白话」。这些都在把模型往辞藻上推。

### 做什么

**1. 提示词新增【语言——朴素直白】一节**（位置：`prompts.py`，紧跟在【叙事质量】之后）。要点：

- 旁白用平实的现代白话：说清楚谁做了什么、看到了什么。一句话能说明白的，不拆成三句。
- 人物说话像真人：先说事。不在每句台词前后加神态、眼神、语气的描写。
- 不替人物解释内心（「她似乎想起了什么」「眼中闪过一丝复杂」）。想表达情绪，就写他做了什么、说了什么。
- 不用「似乎、仿佛、宛如、难以言明、不易察觉、若有所思」这类含糊的修饰来制造气氛。
- 世界观的【叙事风格】（如古风）只决定用词的年代感和称呼，不改变上面这些要求。
- **旁白和人物分开约束**：旁白一律朴素；人物按各自的档案说话（见 C4），某位老先生可以文雅，但那是他个人的特点。

**必须附上对照例子**（模型看例子比看规则管用）。至少三组，直接写进提示词：

| 不要这样写 | 要这样写 |
|---|---|
| 她眸光微动，似有千言万语，终是化作一声轻叹：「你来迟了。」 | 「你怎么才来？」 |
| 掌柜的嘴角勾起一抹意味深长的弧度，指尖在算盘上轻轻一拨：「这个价，怕是不妥。」 | 掌柜摇头：「这个价不行。再加二十。」 |
| 夜色如墨，寒意仿佛顺着衣领渗入骨髓，你心头掠过一丝难以名状的不安。 | 天黑了，很冷。你觉得不对劲：巷子里太安静。 |

同时把【叙事质量】里「写具体的动作、声音、气味、触感与画面」改成「需要时写一两个具体的细节，不要堆砌」；【内容尺度】里的「保持文学性」改成「写得自然」。**【内容尺度】的其他内容，尤其是「底线」那一行，一个字都不要动。**

**2. 文风档位**。状态里新增 `world.prose`，取值 `朴素`（默认）/ `标准` / `文学`：

- `朴素`：使用上面整节。
- `标准`：只保留「不替人物解释内心」「台词先说事」两条。
- `文学`：不加这一节（即现在的行为）。

`build_system_prompt` 按档位拼接。网页开局页的「手动输入」和「AI 生成」两个表单各加一个三选一控件（`st.segmented_control`，默认朴素），写入模板的 `world.prose`。旧存档没有这个字段时按 `朴素` 处理。

**3. 套话统计**（新文件 `style_metrics.py` + `scripts/style_report.py`）：

- `CLICHES`：一份正则清单，至少覆盖：眸、眼中闪过、嘴角(勾起|上扬|微扬)、一丝、一抹、似乎、仿佛、宛如、不易察觉、难以(言明|名状|言喻)、意味深长、若有所思、微微一(怔|愣|顿)、深吸一口气、空气(仿佛)?凝固、心头(一|掠过)、千言万语。
- `cliche_rate(text)`：每千字命中次数。
- `avg_sentence_len(text)`：按「。！？」切分后的平均句长。
- `dialogue_tag_rate(text)`：台词前后 15 个字内带神态描写（命中 `CLICHES`）的台词占比。
- 脚本：`scripts/style_report.py --slot <槽>` 读 `.db` 的 `turns.narrative`（没有 `.db` 时读 `history_*.json`），输出三项指标和出现最多的 10 个套话。

只统计，不改写模型的输出。

### 验收

- `build_system_prompt` 在 `朴素` 档包含新一节和三组对照例子；`文学` 档不包含；缺字段时等同 `朴素`。
- 「底线：涉及性的角色一律是成年人」原文仍在（现有测试会检查）。
- `cliche_rate("她眸光微动，嘴角勾起一抹笑。")` 大于 0；`cliche_rate("你怎么才来？")` 等于 0。
- `docs/style_eval.md` 记录改动前后的三项指标（见 C7）。

## C2 角色档案：字段与冻结

### 现状

`characters[名]` 现在有：`description`、`attitude_toward_player`、`location`、`status`、`aliases`、`affinity`、`met_turn`、`interactions`、`memories`（最多 8 条）。没有性格和说话方式，所以所有人说话一个样。

### 做什么

**1. 新字段**（位置：`world_state.py`，清洗逻辑放进 `_sanitize_character` 一带）：

```python
characters[名] = {
    ...现有字段...,
    "trait": "一句话特点",            # ≤20 字。路人也有；模型首次登场时可以写
    "appearances": 7,                 # 出场次数，代码累加
    "profile": {                      # 只有升格后的角色才有（见 C3）
        "identity":    "内门师姐，丹堂执事",      # ≤40 字
        "personality": "谨慎，重承诺，不愿欠人情", # ≤60 字
        "speech":      "句子短，直接回答；不熟时不主动解释私事",  # ≤60 字
        "cares":       "丹堂的差事；弟弟的病",     # ≤40 字，在意的事
        "bottom_line": "不替别人承担明知可以避免的风险",  # ≤40 字
        "sample_lines": ["今晚别走后山。有人守着。", "药我放这儿了。答应你的。"],  # 2~3 句，每句 ≤30 字
        "goal":  "凑齐弟弟的药费",     # ≤40 字，当前目标（可变）
        "mood":  "焦躁",              # ≤12 字，当前情绪（可变）
        "locked_turn": 23,            # 档案生成的回合
        "revisions": [                # 最多保留 5 条
            {"turn": 61, "field": "personality", "old": "...", "new": "...", "reason": "..."}
        ],
    },
}
```

**2. 谁能写什么**：

| 字段 | 模型能否通过 `update_world_state` 写 | 说明 |
|---|---|---|
| `trait` | 能，**仅在该字段为空时** | 首次登场给一个特点 |
| `profile.goal`、`profile.mood` | 能（工具里是 `characters.<名>.goal` / `.mood`） | 随剧情变化；角色还没有档案时忽略 |
| `profile` 的其余字段 | **不能** | 只由 C3 的档案生成调用写入，写入后冻结 |
| `appearances`、`locked_turn`、`revisions` | 不能 | 系统字段 |

`tools.py` 的 `characters` 条目里增加 `trait`、`goal`、`mood` 三个可选字符串字段，并在说明里写清楚「性格、说话方式由系统生成，不能在这里修改」。

**3. 出场次数**：每回合提交时，叙事或玩家输入里出现了角色的名字或别名，或本轮更新里改动了该角色，就把 `appearances` 加 1（每回合每人最多加 1）。放在 `game._commit` 里，纯代码。

**4. 人物转变**（冻结之后唯一的修改途径）：工具新增 `character_development`：

```json
[{"subject": "陆青鸢", "field": "personality", "new": "……", "reason": "弟弟病逝后，她不再相信宗门"}]
```

代码校验，任何一条不满足就整条忽略：

- 角色存在且已有档案；
- `field` 只能是 `personality` / `speech` / `cares` / `bottom_line`（`sample_lines` 不能直接改，见下）；
- `reason` 非空且 ≥ 8 个字；
- 同一角色距离上一次转变至少 `CHARACTER_DEV_COOLDOWN = 30` 回合；
- 同一回合同一角色只接受一条。

通过后写入新值、追加 `revisions`、清空 `sample_lines` 并标记 `profile_pending = "refresh_lines"`，下一次 C3 的调用只重新生成例句。

开关：`PROFILE_LOCK = True`。设为 `False` 时冷却降为 0（方便以后调成「角色变化更活跃」）。

### 验收

- 模型在普通更新里写 `characters.甲.profile.personality` 或 `characters.甲.personality` → 被忽略。
- `trait` 已有值时，模型再写 → 保持原值。
- 冷却期内的第二条 `character_development` 被忽略；`reason` 为空被忽略。
- 通过的转变在 `revisions` 留下旧值、新值、回合和理由。
- 旧存档（角色没有新字段）能正常读档、跑一回合。

## C3 升格与档案生成

### 思路

不在角色首次登场时编完整背景：大多数路人再也不会出现。等角色和主角真的有了持续的交集，再由代码触发一次**单独的**模型调用生成档案。这样主叙事那次调用不会变长。

### 做什么

**1. 升格条件**（位置：`game.py`，在 `_commit` 的状态合并之后检查）。角色没有 `profile`，且满足任意一条：

- `appearances >= 3`；
- 本回合有以他为对象的 `relationship_events`；
- 本回合新增了与他有关的约定（C5）；
- `memories` 已有 2 条以上。

满足就标记 `profile_pending = "build"`。已有档案的角色总数达到 `MAX_PROFILED = 20` 后不再升格。

**2. 生成**。新方法 `Game._maybe_build_profiles()`，在 `_commit` 存档之后调用（和 `_maybe_compress` 同级）：

- 每回合最多处理 **1 个**待生成的角色（按 `appearances` 从高到低）。
- 用 `llm.call_tool`（单独一个工具 `build_character_profile`，schema 就是 C2 的档案字段，去掉系统字段）。假 LLM 没有 `call_tool` 时直接跳过。
- 输入材料：
  - 世界观背景（截到 300 字）和世界的叙事风格；
  - 该角色的 `description`、`trait`、`attitude_toward_player`、`memories`；
  - `memory.recent` 里提到他的片段；开启 SQLite 时，再加上 `entity_profile(名)` 的最近 5 次出场；
  - **其他已有档案角色的 `personality` 和 `speech`**，并要求「和这些人有明显区别」。
- 给模型的要求（写进这次调用的提示词）：
  - 性格要能指导行为，不要只给「冷傲」「温柔」这种标签；
  - 说话方式写具体：句子长短、直不直接、怎么表达关心或不满；
  - **不要设计口头禅**；
  - 例句 2~3 句，是这个人在日常场合会说的话，朴素直白，不带神态描写；
  - 只根据已有材料合理补全，不要编造与已发生剧情矛盾的经历。
- 代码按 C2 的长度上限清洗结果。缺 `personality` 或 `speech` 时视为失败。
- 成功：写入 `profile`、`locked_turn`，清掉 `profile_pending`，再存一次档。
- 失败：静默并记日志（复用 `storage.log_exception` 或标准 `logging`），`profile_attempts` 加 1，下回合再试；累计 3 次失败后放弃，清掉标记。
- 这一步在回合提交**之后**，它失败不影响、也不回滚本回合。

**3. 世界观自带的角色**（模板里的 `characters`）：不在开局时批量生成。首次在叙事里出现时直接标记 `profile_pending = "build"`，跳过出场次数的门槛。

**4. 同步到 SQLite**（位置：`storage._apply_state_entities`）：`profile` 的 `personality` / `speech` / `cares` / `bottom_line` 作为该角色的事实写入（属性名用「性格」「说话方式」「在意」「底线」）。人物转变会自动留下封口的历史事实，不需要额外代码。

### 验收

- 角色出场 2 次 → 没有档案；第 3 次 → 标记待生成，该回合结束后假 LLM 的 `call_tool` 被调用一次，角色获得 `profile`。
- 同一回合有 3 个待生成角色 → 只生成 1 个，其余下回合继续。
- 假 LLM 返回缺 `speech` 的结果 → 不写入，`profile_attempts == 1`；连续 3 次后不再尝试。
- `call_tool` 抛异常 → 本回合正常完成，状态和对话都已保存。
- 传给生成调用的消息里包含其他已有档案角色的说话方式。

## C4 在场人物卡片进入提示词

### 现状

`world_state.to_summary()` 用 `_characters_for_summary` 最多列 12 个角色，每人一行描述加 3 条往事，在场和不在场的写法一样。

### 做什么

**1. 分成「相关」和「其他」两组**（位置：`world_state.py`）：

- **相关**：位置在当前地点的；玩家本次输入里点到名字或别名的；上一回合叙事里出现的。最多 `MAX_CARDS = 4` 人，按这个优先级取。
- **其他**：剩下的，最多 8 人，每人一行。

`to_summary` 需要多接收一个参数（玩家本次输入），由 `prompts.build_turn_messages` 传入。

**2. 相关角色给完整卡片**（有档案时），每张控制在 `CARD_MAX_CHARS = 180` 字以内，超长时按「往事 → 在意 → 目标」的顺序裁掉：

```
- 陆青鸢（内门师姐，丹堂执事）｜对你：友善，好感=中｜在丹堂
  性格：谨慎，重承诺，不愿欠人情。底线：不替别人担明知能避免的风险。
  说话：句子短，直接回答；不熟时不主动解释私事。
  例句：「今晚别走后山。有人守着。」「药我放这儿了。答应你的。」
  眼下：凑齐弟弟的药费；焦躁。
  未了：她答应三日内送来药材（第 23 回定下，已过 5 天）。
  往事：你替她隐瞒过行踪。
```

没有档案的相关角色：现有的一行描述，加上 `trait`。

**3. 其他角色一行**：`- 赵执事（外门管事）｜对你：敌视｜在外门执事堂`。

**4. 系统提示新增【人物档案的用法】一节**（`prompts.py`）：

- 人物说话、做事要符合档案里的性格和说话方式。
- 例句只是语气参考，**不要照抄，也不要让人物反复说同一句话**。
- 人物只知道自己经历过或合理能打听到的事。
- 不要向玩家复述档案内容，不要用旁白总结人物性格（「她一向谨慎」）。通过他说的话、做的事体现。
- 有未了的约定时，人物会按自己的性格去处理（兑现、催促、回避、翻脸），不必每次见面都从头复述来龙去脉。
- 性格决定「怎么说、提什么要求」，不决定判定的成败；成败仍以系统结算为准。

### 验收

- 当前地点有 6 个带档案的角色 → 摘要里只有 4 张卡片，其余在「其他」里各占一行。
- 不在场、但玩家输入里点了名的角色 → 出现在卡片组。
- 任何一张卡片不超过 180 字；带档案的卡片里有「说话：」和「例句：」。
- 没有任何角色有档案时，摘要的角色部分与 v2.24 的信息量相当（旧存档不退化）。
- 玩家可见的 `to_player_summary()` 里**不出现**性格、说话方式、例句（那是给模型看的）。

## C5 未了事项（约定）

### 思路

「谁答应了谁什么、到没到期、兑现没有」是让人物显得有记性的关键。做成结构化的表，由代码管期限。

### 做什么

**1. 状态**（`world_state.py`）：新增 `state["promises"]`，列表，每项：

```python
{"id": "p3", "from": "陆青鸢", "to": "玩家", "content": "三日内送来回气丹的药材",
 "made_turn": 23, "made_day": 47, "due_days": 3,       # due_days 可以没有
 "status": "open",                                     # open / kept / broken
 "closed_turn": None}
```

**2. 工具字段**（`tools.py`）：

- `promises_add: [{"from", "to", "content", "due_days"?}]`：`from` 和 `to` 之一必须是 `玩家`，另一方必须是已知角色（或本次更新里新出现的角色）。`content` ≤ 60 字。`due_days` 为 1~3600 的整数。
- `promises_update: [{"id", "status"}]`：`status` 只能是 `kept` 或 `broken`，且该约定当前必须是 `open`。

**3. 代码规则**：

- `id` 由代码分配（`p1`、`p2`…），模型给的 `id` 在新增时忽略。
- 同一对人之间内容完全相同的 `open` 约定不重复添加。
- `open` 的约定最多 `MAX_OPEN_PROMISES = 20` 条，满了就拒绝新增并往 `event_log` 记一条。已了结的只保留最近 20 条。
- **期限**：有 `due_days` 且 `calendar.days > made_day + due_days` 时算「逾期」。逾期**不自动判定为失约**，只在摘要里标出「已逾期 N 天」，由人物按性格反应；是否算失约仍由模型用 `promises_update` 声明。
- **了结的后果由代码执行**（在 `dynamics.py` 加两个事件）：
  - 玩家守约（`from == "玩家"` 且 `kept`）：对方好感 `+8`；
  - 玩家失约（`from == "玩家"` 且 `broken`）：对方好感 `-12`；
  - NPC 守约或失约：不自动改好感。
  - 这些变化和同回合的 `relationship_events` 一起受「单轮 ±30」的限制。
- 判定前的草稿更新里出现这两个字段时，按 `game.py` 现有的预掷骰白名单规则处理（和其他状态字段一样：草稿里不生效，结算后的那次更新才生效）。检查 `merge_updates` 对新字段的处理。

**4. 进入摘要**：

- `to_summary()`：相关角色的卡片里有「未了」一行（C4）；另有一个总览段落列出全部 `open` 约定，逾期的排在前面。
- `to_player_summary()`：列出 `open` 的约定，写法定性（「陆青鸢答应送来药材，已逾期」），不写编号。

**5. 界面**（唯一允许改动 `render_world_panel` 的地方）：在「旅途线索」卡片里，当前目标之后追加未了的约定，每条一行，**复用现有的 `.bullet` 类**，不新增 CSS。逾期的在末尾加「（已逾期）」。

**6. 同步到 SQLite**：每条约定作为 `kind='promise'` 的实体（名字用 `id`），事实属性为「内容」「状态」。状态变化会自动留下历史。

### 验收

- `promises_add` 后状态里有一条 `open` 约定，`id` 由代码生成，`made_turn` / `made_day` 正确。
- 双方都不是 `玩家`，或另一方是未知角色 → 拒绝。
- 日历推进到期限之后 → 摘要里出现「已逾期」，`status` 仍是 `open`。
- 玩家失约 → 对方好感下降 12；同回合再加一条「背弃」关系事件 → 总变化不超过 30。
- 对已了结的约定再次 `promises_update` → 忽略。
- 网页「旅途线索」里能看到未了的约定（`AppTest` 里断言 markdown 包含约定内容）。

## C6 标出「这是他的说法」

### 做什么

现在角色的 `memory` 一律当作事实记下来。某人说「玉佩不是我拿的」，这只是他的说法。

- `tools.py`：`characters.<名>` 增加可选字段 `memory_kind`，取值 `event`（默认）或 `claim`。
- `world_state._add_memory`：`claim` 的条目存成带标记的结构，或在文本前加固定前缀 `【其说法】`（二选一，选改动小的）。
- 摘要里显示为「他的说法（未证实）：……」。
- 系统提示【人物档案的用法】里加一句：人物自己说的、尚未证实的话，用 `memory_kind: "claim"` 记录，不要当作事实。

**不在本次范围**：完整的「每个角色知道什么」的隔离。那需要重新设计幕后进展的可见范围，留到以后。

### 验收

- `memory_kind: "claim"` 的往事在 `to_summary()` 里带「未证实」字样；默认情况不带。

## C7 评估

### 1. 文风（不需要 API，可进 CI 的部分是单元测试；报告手动生成）

对同一世界观、同一串玩家输入（准备一份 20 条输入的固定剧本，存为 `tests/fixtures/style_script.json`），用真实模型各跑一遍：改动前的提示词（`world.prose = "文学"`）和改动后（`朴素`）。用 C1 的脚本统计，写进 `docs/style_eval.md`：

| 指标 | 文学档 | 朴素档 |
|---|---:|---:|
| 套话每千字次数 | | |
| 平均句长 | | |
| 带神态描写的台词占比 | | |

目标参考：朴素档的套话频率不到文学档的一半。跑这一步要花 API 费用，**由作者手动执行**；脚本要准备好：`scripts/style_ab.py --script tests/fixtures/style_script.json`。没有 API Key 时脚本给出清楚的提示并退出。

### 2. 人物区分度盲测（需要 API，手动执行）

新脚本 `scripts/voice_blind_test.py --slot <槽>`：

1. 从存档里取所有带档案的角色（至少 4 个，否则提示人数不够）。
2. 准备 3 个固定情境（如：「主角深夜来敲门借钱」「主角当众顶撞了他」「主角送来一份他正需要的东西」）。
3. 对每个角色、每个情境，调用一次模型：只给这个角色的卡片，让他说一句回应（≤40 字，只要台词）。
4. 把台词打乱、去掉名字，再调用一次模型当评审：给出全部角色的卡片和一句台词，让它判断是谁说的。
5. 输出猜中率，以及最容易被混淆的两个角色。

随机猜中率是 `1 / 角色数`。目标参考：5 个角色时猜中率 ≥ 70%。结果写进 `docs/voice_eval.md`。

### 3. 回归

全量测试保持全绿。新增用例覆盖 C1~C6 各项的「验收」。

## 需要作者决定的两处（已按默认值写入，改起来只是常量）

- **角色稳定还是多变**：默认稳定。性格生成后冻结，转变需要理由且间隔至少 30 回合（`CHARACTER_DEV_COOLDOWN`）。想让角色变化更活跃，就调小这个数或把 `PROFILE_LOCK` 设为 `False`。
- **默认文风档位**：默认 `朴素`。
